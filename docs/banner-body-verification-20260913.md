# 条幅、正文颜色与性能验证（2026-09-13）

本地版本 `2.98.2-page0x00.3`。保留已经整合的作者 2.98.2 功能。本轮不 commit、不 push，也没有覆盖酒馆安装目录。

## 四类根因

1. **名称截断**：过去名称直接交给原生 `<select>` 绘制，桌面/移动原生规则存在 ellipsis；只改外层或加低优先级覆盖无法保证实际显示。当前真实 Vue 模板保留完整选项和原生选择事件，另设单行可见名称，显示层去除省略符号，三个可见容器均硬裁切。Chromium 实测：四个节点的 `text-overflow` 均为 `clip`；原生 select 的 `overflow` 计算值仍会是 `visible`，这是原生控件的绘制行为，因此不能再依赖它裁切文字。它的选中文字完全透明，实际可见区域、字段、文字 span 的 `overflow` 均为 `hidden`。
2. **重复入口**：二改控制器另建了顶部“条目”按钮，占用了名称空间。已从创建和绑定逻辑删除；原来的铅笔左上方空白区域仍切换列表，预设工具、分支、铅笔功能保留。
3. **宽度失效**：旧比例默认、DOM 宽度和中控 profile 存在不同来源，重挂载/刷新容易读回默认值。当前中控模型是唯一请求来源，CSS 只限制可见宽度。本轮真实浏览器还复现了“长名称铺满后切回短名称，计算偏大”：旧把手避让间距被误算成固定内容。现在先测普通头部，再根据新宽度判断是否需要避让。
4. **正文白字**：实际“内容正文”节点是 `.prompt-editor__textarea[data-v-01bebc6e]`，不是旧规则中的 `.prompt-card__content` / `.prompt-item__content`。原生 scoped 规则显式使用 `color:var(--pm-text-primary)`；当该变量为白色，正文会覆盖外层的深色文字。即使改成美化 `--pmm-theme-text`，正文保留的原生背景也未必与外层皮肤相同，例如紫黑日间的浅色正文框。桌面美化过渡还会临时清空背景、改用前后伪元素层，直接读取这一中间态也会误判。现在在正文挂载/主题提交时读取实际背景，过渡面板采用已有的目标底色，合成透明底色，仅选择正文前景色；`color` 与 `-webkit-text-fill-color` 同步。原生背景颜色过渡结束/取消时，再通过事件校正一次，只结束正文前景色的过渡，不影响材质动画。临界对比度使用更明确的深/浅文字，为现有阴影和透明合成留出余量。

正文修复集中在原有 `PMM_APPROVED_ENTRY_TEXT` 位置，没有再添加第二套文字覆盖块。没有改背景、透明度、边框、阴影、模糊、布局或冻结材质。折射玻璃/紫黑原 token 与 `PMM_FROZEN_VISUAL_BASELINE` 哈希保持原样。

## 自动与手动宽度

| 状态 | 行为 |
| --- | --- |
| 当前 mobile/desktop 宽度组没有有效记录 | 第一次能测量已展开头部时，计算完整名称 + 保留按钮 + 间距，限制在可视区域内 |
| 自动模式下名称/整体字号变化 | 标记需要重算，合并为一次测量；收起或拖动中延后 |
| 自动模式下横竖屏变化 | 按新的可视区域计算一次 |
| 已计算默认，内容及 profile 未变化 | 关闭重开、刷新、原生节点重挂载复用结果 |
| 中控预览手动宽度 | 立即退出自动预览，名称/字号变化不能改宽度；取消可撤回 |
| 中控保存手动宽度 | `customized.floatingWidth=true`，`values.floatingWidth` 持久化；刷新/重开/重挂载优先使用 |
| 恢复默认 | 清除当前组手动标记、自动宽度及内容记录，重新计算；保存后持久生效 |

现有宽度分组仍是 mobile / desktop，横竖屏位置 profile 保持原机制，不另造一套宽度存储。`bannerAutoContent` 记录自动测量对应的名称和字号，用于重载复用。回调同时校验 profile、手动标记和测量前的宽度；过期结果不能反写新状态。

## 为什么前两轮可能看不到变化

- 旧测试主要验证源码字符串和 VM 行为，不能证明 Chromium 原生 select 的实际绘制或最终 CSS 级联；也没有覆盖把手避让从满屏退回普通宽度的情况。
- 仅修改主题 token 或不存在的正文类名，不一定命中真正的 textarea。直接套用外层皮肤文字色还会漏掉正文与外层背景不同的情况。
- 本轮只读检查发现，本机酒馆安装目录 （酒馆 third-party 下的旧工坊目录） 的 manifest 仍是 `2.97.36`，且没有 `PMM_APPROVED_ENTRY_TEXT`、`pmm-preset-name-text` 修复。它和当前 `preset-workshop` 工作区不是同一目录。这个事实能解释该安装目录为何不显示本地修复；不能据此断言你所有测试设备都加载了它。按照本地保留要求，本轮没有替换该目录。

## 检查与范围

新增 `scripts/test-banner-browser.mjs` 和 `scripts/lib/browser-cdp.mjs`：通过 CDP 连接独立 Chromium，不为扩展增加运行依赖。测试使用发布包内真实组件 CSS（含 scoped 样式）、对应 DOM 结构和完整中控/悬浮/美化模块。可用时加载本机酒馆的实际 Font Awesome 字体。

- 390×844、844×390、800×1100、1100×800、1440×1024 五类视口分别检查最终 clip、透明原生选中项、无重复按钮、左上入口、首次完整名称宽度、长名称达到视口才截断、保存/reload/重挂载和恢复默认。
- 八种美化/日夜组合分别放在浅色、深色酒馆背景下，再分别验证触屏/桌面路径，共 32 种情况读取最终 `color` 和 `-webkit-text-fill-color`；从 Chromium 截图采样正文空白处实际背景，检查可读对比度，包含透明背景合成。
- 移除/恢复正文颜色规则，比较背景、透明度、边框、阴影、模糊、尺寸、间距和字号等计算值，证明修复没有改变材质或布局。
- 统计空闲 30 帧及拖动 60 帧的 `getBoundingClientRect`、`getComputedStyle`、`measureText` 次数。没有定时轮询；名称改用 Vue 的 `watch(...,{flush:'post'})`，删除额外名称 MutationObserver；正文使用 Vue 挂载通知和现有主题事件。
- 原有运行回归补充自动名称/字号变化、过期回调、手动优先、自动上下文持久化、关闭重开和原生节点先移除再挂载。

运行方式：启动独立 Chromium，开启 `--remote-debugging-port=9222`，执行 `npm run test:banner-browser`。可用 `PMM_CDP_URL` 指定已有测试浏览器地址。浏览器包/依赖仅解压在 Termux 临时目录，未安装到项目或修改系统包。

浏览器测试不启动完整酒馆聊天后端，不替代实际聊天切换、其他扩展叠加和设备触屏验收。

## 实机验收

1. 先确认实际加载本地版本 `2.98.2-page0x00.3`，不是 GitHub 上未同步的版本。只刷新旧安装目录不会获得本地修复。
2. 在手机、平板横竖屏、电脑分别用“诸神黄昏2.17”：恢复默认后完整显示；手动缩窄到只能容纳部分名称，确认单行直接截断，无 `...` / `…`。
3. 顶部没有重复“条目”按钮；点击铅笔左上方原区域连续展开/收起列表；铅笔、预设和分支选择仍可用。
4. 中控先解锁“条幅宽度”，设为容易辨认的宽度并保存：关闭重开、刷新、切聊天使原生条幅重新挂载、横竖屏后仍保留。再换长名称/改字号，保存宽度不能变化。
5. 恢复默认并保存：宽度按当前内容计算；自动模式下换长短名称或改整体字号才跟随变化，再关闭重开/刷新确认同样内容保持。
6. 四种美化各切日夜，展开“内容正文”，输入并修改一段文字，确认文字和输入内容清楚、背景材质未变。切换期间连续操作中控和拖动悬浮球，确认没有新增停顿。
